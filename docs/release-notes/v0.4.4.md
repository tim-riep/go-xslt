go-xslt 0.4.4 is a performance release: three more measured rounds on the engine (the thirteenth to fifteenth), each in two parallel halves, judged on the whole engine with the same rule as before — no workload may get slower, allocate more, use more memory or execute more instructions, and every output stays byte-identical. Every W3C conformance number is the same as in 0.4.3.

## Engine

- **Compact numbers.** An xs:decimal and an xs:integer are held as an int64 inside the same 64-byte atomic value whenever the value fits — nearly always — with addition, subtraction, multiplication, division, `idiv`, `mod`, `sum`, `avg`, rounding, comparison, casts and formatting done in integers and checked bit for bit against the big-number path; `format-number` renders them in integer arithmetic. Number formatting executes 37 % fewer instructions and makes 64 % fewer allocations; deep recursion summing decimals 17 % fewer instructions and 62 % fewer allocations.
- **Node sets without boxing, step by step.** A one-step path read by a predicate, a comparison, a built-in argument, `xsl:value-of`, an attribute value template, an `xsl:if` test, a key or a sort lives in a scratch array; a path of several steps builds its intermediate sets in lent arrays; a string parameter's one plain node is passed as the node itself; a plain node cast to a number or date skips the intermediate untyped value. XPath 1.0 predicates: 13 % fewer instructions, 69 % fewer allocations; string functions 17 % and 53 %; sorting 20 % and 78 %; stylesheet function calls 11 % and 34 %.
- **`xsl:number`** counts on from the last sibling it numbered: numbering with `position()`/`last()` executes 80 % fewer instructions and takes 73 % less CPU time.
- **Grouping and iteration.** `generate-id(A) = generate-id(B)` compares the nodes; a group-by key that is one plain node finds its group by its string alone; an `xsl:iterate` iteration recycles its frame and `xsl:next-iteration` is one allocation; map calls take their key without argument slices. Grouping into a map with JSON output: 27 % fewer instructions, 57 % fewer allocations; `xsl:iterate` over a map: 34 % and 66 %, 40 % less CPU time; 200 transforms in one process: 26 % and 62 %.
- **Readers, serializer, validator.** The tokenizer reads names with one table look per byte and tells the parser which attribute values need whitespace normalization; both readers take tokens from the tokenizer's own fields, fill their open frames in place and share whitespace runs; the stream reader interns recurring names through a small cache and carries an element's first text child in the element's own allocation; the serializer writes a start tag and an end tag each in one call and decides the output method, the HTML version and its attribute classes once; the XSD validator marks attribute uses by position, caches each simple type's primitive, whitespace handling and facet flags at compile time, evaluates identity constraints on unboxed node sets with key tuples in one arena, and looks a type's child model up once; the compiler walks a stylesheet once for its reference checks and gathers a literal result element's namespaces without maps. Copying a 37 MB document: 17 % fewer instructions; XSD 1.0 validation 26 % fewer instructions and 12 % less CPU time; XSD 1.1 validation 18 % fewer instructions, 43 % fewer allocations, 20 % less CPU time; streaming 21 % fewer instructions, 25 % fewer allocations; HTML output 21 % fewer instructions, 21 % fewer allocations; compiling DocBook's stylesheet 9 % fewer instructions.
- Measured on the whole 23-workload set against 0.4.3 (`go run ./scripts/perfab -a v0.4.3 -b v0.4.4`, 8 alternating runs, then `-ir`): every workload executes fewer instructions (between 4 % and 80 % fewer) and takes less CPU time (between 0.1 % and 73 % less); peak memory and allocated bytes are at or below 0.4.3 on every workload; every output is byte-identical. The candidates that were tried and rejected are documented on the performance page.
